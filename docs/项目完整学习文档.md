# MewCode Agent 完整学习文档

> 目标：用一份文档理解本项目的技术选型、功能边界、核心实现和面试表达。
>
> 文档基于当前仓库代码、测试和 M01–M17 验收记录整理。描述“已实现”时以源码和实际验收为准；MockProvider 的演示只能证明协议和工程流程，不代表真实模型可以完成任意编程任务。

## 1. 项目一句话介绍

MewCode Agent 是一个使用 TypeScript 和 Node.js 实现的本地 CLI Coding Agent。用户通过自然语言提出编程任务，模型通过统一协议提出文本回复或工具调用，程序经过参数校验、路径检查、权限决策和必要审批后执行文件、搜索、Shell 或 MCP 操作，再把结构化结果回传模型，直到任务完成、失败、取消或达到预算。

最重要的设计原则是：

> 模型负责提出计划，程序负责验证和执行；模型输出、文件内容或外部服务返回值都不能提升权限。

## 2. 项目解决了什么问题

单纯的聊天模型只能生成建议，不能可靠地完成“定位文件—修改代码—运行测试—根据结果纠错”这一闭环。一个可用的 Coding Agent 至少需要解决以下问题：

1. 如何接入不同模型服务，并把不同的流式协议转换成统一事件。
2. 如何把模型的工具调用安全地映射到本地文件和进程。
3. 如何避免越界读写、危险命令、重复执行和覆盖并发修改。
4. 如何管理长任务的上下文、会话恢复、记忆和故障。
5. 如何支持 MCP、Skill、Hook、SubAgent、Git Worktree 和 Teams 等扩展能力。
6. 如何用确定性测试证明实际文件、进程退出码、权限和恢复行为。

本项目聚焦本地 CLI 和可验证工程行为，没有把目标扩大成 Web 平台、数据库编排系统或操作系统级沙箱。

## 4. 总体架构

```text
用户 / 终端
    ↓
CLI / Ink UI
    ↓
Core：Conversation、AgentLoop、Context、Session、Memory
    ↓
Provider：Mock、OpenAI-compatible、Anthropic
    ↓
ToolExecutor：Schema、路径、权限、审批、Hook、审计
    ↓
内置工具 / MCP / Shell / 文件系统 / 子进程
```

扩展协作能力位于 Core 和 Tools 之上：SubAgent 使用受限的子执行器，Worktree 为写入任务绑定独立 Git 工作树，Teams 使用持久成员、任务依赖和消息队列调度多个任务。

### 4.1 依赖边界

- `core`、`config`、`providers` 不依赖 CLI 或 UI。
- UI 只订阅事件、显示状态和提交用户操作，不直接读写文件或执行 Shell。
- Provider 只负责协议适配，不负责路径权限。
- 所有模型、Hook、MCP 和子 Agent 的执行都必须经过统一工具入口。
- `shared` 只保留错误、脱敏、边界文件等基础能力。

## 5. 两种运行模式：chat 与 run

### 5.1 `chat`

`chat` 是普通多轮对话。 `Conversation` 保存系统消息、用户消息和模型回复，支持流式文本、模型切换、`/clear`、`/compact`、`/model`、`/permissions` 等命令，但不会向模型开放文件、Shell 或外部工具。

### 5.2 `run`

`run` 是 Agent 任务。 `AgentLoop` 向模型发送工具 Schema，接收工具调用，调用 `ToolExecutor` 执行，并把结果作为 `role: tool` 消息回填。它支持模式、预算、超时、取消、会话、上下文压缩和审批。

常用命令：

```powershell
npm ci
npm run dev -- --help
npm run demo -- "学习 Agent 的执行流程"
npm run chat -- --provider mock --model mock-v1 "你好 MewCode"
npm run agent -- --provider mock --model mock-v1 "检查项目入口"
npm run dev -- tool --help
```

`demo` 是固定的离线流式演示；`chat` 适合观察文本事件；`run` 才是完整工具 Agent。

## 6. 核心执行闭环

一次典型任务可以概括为：

```text
用户目标
  → 组装系统提示、项目指令、记忆、Skill、工具 Schema
  → Provider 流式返回文本/工具调用分片
  → ToolCallBuffer 组装完整调用
  → 校验调用协议和工具参数
  → ToolExecutor 检查路径、模式、规则、Hook、审批
  → 执行文件、Shell 或 MCP
  → 生成 callId 关联的结构化结果
  → 回填模型上下文
  → 下一轮，或正常结束
```

核心接口位于 `src/providers/types.ts`：

```ts
interface LLMProvider {
  readonly id: string;
  readonly capabilities: { streaming: boolean; toolCalling: boolean };
  stream(request: LLMRequest, signal: AbortSignal): AsyncIterable<LLMEvent>;
}
```

统一事件包括：

- `text_delta`：流式文本片段。
- `tool_call_delta`：工具调用的编号、名称或参数片段。
- `usage`：输入和输出 token，用量缺失时使用保守估算。
- `continuation`：Responses 或 Anthropic 的续传数据。
- `finish`：`stop`、`length` 或 `tool_calls`。

### 6.1 为什么不能收到文本就直接执行

工具参数可能被分成多片，也可能被模型截断或产生非法 JSON。项目先用 `ToolCallBuffer` 完整组装调用，再验证 `callId`、工具名、JSON、结束类型和批次一致性。只要整批协议无效，就不执行该批工具；单个工具的业务失败则会作为结果回填，让模型纠错。

### 6.2 停止条件

AgentLoop 在以下情况下结束：

- 模型没有工具调用并正常输出文本。
- 模型输出长度达到上限。
- 达到最大轮数、总 token 或上下文大小。
- 工具连续失败达到阈值。
- 超时、用户取消、Hook 阻止或协议错误。

`completed` 只表示引擎正常完成协议，不等于模型解决了任意业务目标。是否做对，要看文件 diff、真实测试输出和工具证据。

## 7. 工具系统

项目提供六个主要内置工具：

| 工具 | 功能 | 关键保护 |
| --- | --- | --- |
| `ReadFile` | 读取文本、行号、范围和大小限制 | 项目根、路径解析、二进制识别 |
| `WriteFile` | 创建或覆盖文件 | 原子替换、创建/覆盖区分、diff 和 revision |
| `EditFile` | 精确文本替换 | 默认要求唯一匹配和 expectedRevision |
| `Glob` | 有界文件枚举 | 固定前缀、隐藏文件策略、结果数量限制 |
| `Grep` | 正则或字面量搜索 | rg、范围授权、无匹配和失败区分 |
| `Bash` | 执行 Shell 命令 | 明确 shell、cwd、超时、输出和退出码 |

工具定义包含名称、描述、Zod Schema、读写效果、支持模式、`prepare` 和 `run`。 `prepare` 负责解析最终目标和预览，`run` 负责实际执行。

统一执行顺序是：

1. 校验 `callId` 和工具输入 Schema。
2. 解析项目相对路径、符号链接、junction、Windows 大小写和 UNC 边界。
3. 根据工具效果计算权限决策。
4. 执行 `PreToolUse` Hook（如有）。
5. 如果 Hook 修改了输入，重新校验、准备目标和计算权限。
6. 对需要 `ask` 的动作显示最终参数、cwd 或 diff，等待一次或当前进程授权。
7. 执行工具并检查取消、超时和实际文件状态。
8. 执行 `PostToolUse` Hook，写入审计并返回结果。

## 8. 权限与安全设计

项目使用五层防御：

| 层 | 检查内容 |
| --- | --- |
| 模式 | `plan` 只读，`default` 按规则，`accept-edits` 允许项目内常规编辑 |
| 路径 | 规范化绝对路径，限制在项目根和授权范围 |
| 操作 | 区分 read、write、shell、external，危险或未知动作需要审批 |
| 授权 | `allow`、`ask`、`deny`，优先级为 deny > ask > allow |
| 执行 | 超时、取消、输出上限、审计、工作树和进程清理 |

权限来源包括用户配置、项目配置、CLI 和父 Agent。项目规则可以收紧权限，不能通过模型文本放宽父级 deny。 `--approve` 只是提供管理或委派操作的显式批准，也不能覆盖 deny、Plan 或子任务的 Shell 审批。

### 8.1 精确授权

一次授权绑定工具名、完整输入、最终目标、预览、Shell、权限谱系和策略版本。 `once` 只允许当前调用；`session` 只在当前执行器进程中复用。参数、路径、diff、模式或父权限发生变化，旧授权不能复用。授权不跨进程保存。

### 8.2 文件版本保护

读取文件时返回 revision。编辑或覆盖时必须带 `expectedRevision`，执行前再次比较当前 revision。文件已被其他进程修改时返回冲突，避免静默覆盖。写入使用原子替换，但这仍是单文件保护，不能构成多文件事务。

### 8.3 Shell 的真实边界

Shell 的 cwd 会绑定项目或工作树，命令有超时、取消和输出限制，但获准 Shell 仍拥有当前用户主机权限。Git Worktree 也不是操作系统沙箱，不能阻止网络、仓库外路径或主机级破坏。因此面试时要明确说：这是工程权限和审计边界，不是 OS 级安全隔离。

## 9. 配置与提示系统

配置按已知字段合并，来源通常包括默认值、用户文件、项目 `.mewcode/config.yaml`、环境变量和 CLI 覆盖。未识别字段会被拒绝，密钥只保留环境变量名称。

项目指令使用根目录 `AGENTS.md`，兼容检查 `CLAUDE.md`。访问某个目录、文件、Glob 前缀或 Bash cwd 时，系统按需发现祖先到目标目录范围内的指令。深层指令只适用于其目录，不能自动扩大权限。

提示内容由系统身份、任务、项目指令、记忆、Skill 元数据和工具定义组成。 `prompt --json` 可以检查来源元数据、预算和实际环境，但不会输出敏感正文。

## 10. 上下文、会话和记忆

### 10.1 上下文压缩

上下文模块先估算输入 token、输出预留和字符大小。当接近窗口阈值时进行本地结构化压缩：保留系统消息、任务目标、最近完整的调用与结果组，并为归档历史保存动作指纹。长工具结果可以溢写到会话存储，只在消息中保留摘要和引用。

压缩不是模型摘要，没有额外模型请求；它会省略细节，归档指纹证明历史身份而不是保证语义无损。需要原文时应读取检查点或溢写结果。

### 10.2 JSONL 会话与恢复

会话把意图、模型回复、工具结果、压缩和完成状态写入 JSONL 检查点。恢复时核验版本、顺序、动作指纹和已执行调用，阻止相同动作仅换一个 `callId` 再执行。

它不能承诺 exactly-once：Shell 或 MCP 的外部成功与本地日志落盘之间可能崩溃，外部系统没有参与本地原子事务。因此不确定时应先核验外部状态，再决定恢复或重试。

### 10.3 长期记忆

记忆是有界 Markdown 数据，分用户和项目作用域，支持 `preference`、`convention`、`fact`。只有用户明确确认的内容才能写入；候选提取只识别原始用户消息中的明确前缀，不从模型或工具输出推断事实。读取按查询词和字节预算筛选，密钥、敏感赋值和越界文件会被拒绝。

## 11. MCP、Skill 和 Hook

### 11.1 MCP

MCP Manager 负责配置、stdio/Streamable HTTP 连接、工具发现、命名空间、Schema 编译、调用和关闭。远端工具结果仍要经过本地 Schema、external 权限和生命周期管理，MCP 返回内容不能修改本地权限。

### 11.2 Skill

Skill 是项目或用户目录中的 `SKILL.md`。启动时只建立元数据索引，按名称、描述或显式选择加载正文；资源不会自动无限读取。Skill 提供方法和参考资料，不能授权工具、提升模式或绕过审批。

### 11.3 Hook

Hook 支持 `SessionStart`、`PreToolUse`、`PostToolUse`、`Stop`、`SessionEnd`。脚本以结构化 JSON 交互，PreToolUse 可以返回 `updatedInput`，但修改后会重新走 Schema、路径和权限检查。安全事件失败默认阻止动作，通知事件失败保留工具实际结果。Hook 脚本本身按 Shell 能力审批，Plan 禁止执行。

## 12. SubAgent、Worktree 与 Teams

### 12.1 只读 SubAgent

SubAgent 适合并行探索不同目录。父 Agent 显式开启后，子任务固定 Plan、深度为 1，只开放 `ReadFile`、`Glob`、`Grep`，继承父级 deny 和 Hook 边界。池使用 FIFO 队列和并发上限，父子共享 token 预算；一个子任务失败不会吞掉其他结果，重试必须使用新任务 ID。

### 12.2 Git Worktree

写入子任务使用独立 Git branch 和 worktree。系统记录 owner、任务、基准 ref、路径和状态，并把文件根和 Shell cwd 绑定到对应工作树。结束后汇总真实 diff、未跟踪文件、退出码和测试结果；脏工作树、活动任务和未知文件会阻止回收，不自动合并主分支。

### 12.3 Teams

Teams 在多个成员之上增加持久任务看板、依赖图和消息队列。任务只有依赖满足后才能领取，领取过程防重复；消息使用 `messageId` 去重，成员失败可以显式 retry，恢复时检查成员和工作树，避免重复执行已交付任务。消息不会自动创建或触发无限任务。

多 Agent 不一定更快。并发只能减少独立大任务的墙钟时间，同时增加模型调用、汇总和协调成本；本项目实现了预算和并发边界，但没有宣称真实模型场景的普遍速度或费用收益。

## 13. 测试与验收方法

测试分为三类：

- 单元测试：权限规则、路径、Schema、上下文压缩、记忆和 UI 状态。
- 集成测试：Agent Loop、真实临时文件、Shell、MCP、会话、SubAgent、Worktree 和 Teams。
- 发布与评估：构建产物、安装包冒烟、固定离线五场景和跨平台 CI。

常用检查：

```powershell
npm run typecheck
npm run lint
npm run format:check
npm run check:boundaries
npm test
npm run build
npm run check
```

典型闭环测试会在临时目录中：先把 `sum` 写成减法，模型脚本依次发出 Glob、Grep、ReadFile、EditFile、Bash，EditFile 使用 ReadFile 返回的 revision，Bash 运行 Node 检查脚本，最后断言文件内容、五个工具结果和退出原因。测试证明的是程序执行行为，不能证明真实模型的自主修复率。

项目还覆盖：坏工具调用整批拒绝、Plan 写入阻止、连续失败停止、取消后不执行后续调用、Shell 子进程退出、MCP 关闭、压缩恢复、权限竞态、工作树隔离和团队依赖。

## 14. 一次面试可复述的项目介绍

### 14.1 两分钟版本

我做的是一个 TypeScript 和 Node.js 的本地 CLI Coding Agent。它支持流式对话、文件搜索读写、Shell、MCP、会话恢复以及隔离的子任务协作。核心是一个有界 Agent Loop：模型返回文本或工具调用，程序先组装完整参数并验证协议，再交给统一 ToolExecutor 检查 Schema、路径、权限、Hook 和审批，执行结果通过 `callId` 回填模型，继续下一轮。

我把模型建议和真实执行严格分开。Plan 模式和执行器都会限制写操作；权限采用 deny 优先和精确参数授权；文件修改使用 revision 防止覆盖并发修改；Shell 有 cwd、超时、取消和审计。长任务通过上下文预算、本地压缩、结果溢写和 JSONL 检查点恢复，恢复会阻止已记录动作重复执行，但不承诺外部副作用 exactly-once。

扩展层包含 MCP、按需 Skill、生命周期 Hook、只读 SubAgent、Git Worktree 和 Teams。测试使用模拟 provider 加真实临时文件、进程和本地服务验证工程行为。当前的边界是：Mock 只演示固定协议，真实模型任务成功率和费用没有测量，Worktree 和 Shell 也不是 OS 级沙箱。

### 14.2 十分钟讲解顺序

1. 展示 `README` 和 CLI：解释 `chat` 与 `run` 的区别。
2. 打开 `src/core/agent-loop.ts`：说明流式事件、工具调用组装、回填和停止条件。
3. 打开 `src/tools/executor.ts`：说明 Schema、路径、Hook、审批和执行前二次检查。
4. 打开 `src/security/policy.ts` 与权限测试：解释 deny 优先、Plan 和精确授权。
5. 打开 `src/core/context.ts`、`session.ts`：解释预算、压缩、溢写和恢复防重。
6. 打开 `src/mcp/manager.ts`、`src/tools/hooks.ts`：说明外部工具和生命周期扩展。
7. 打开 SubAgent、Worktree、Teams 代码：解释为什么要隔离和共享预算。
8. 运行固定修复演示，展示真实 diff、退出码和证据。
9. 主动说明真实模型质量、OS 沙箱、自动合并和正式发布仍有限制。

## 15. 高频面试问题与回答要点

### Q1：Coding Agent 和普通聊天有什么区别？

普通聊天只维护文本历史。Agent 会把模型的结构化工具调用交给本地执行器，读取真实结果后回填，直到停止条件。最终正确性要看 diff 和测试，而不是模型最后一句话。

### Q2：为什么不直接执行模型生成的 Shell？

因为流式参数可能不完整、Schema 可能非法，文本也不等于授权。调用必须经过完整组装、输入校验、路径和权限检查、审批与审计。即使通过，Shell 仍有当前用户主机权限。

### Q3：为什么 Provider 要抽象成统一事件？

OpenAI Chat Completions、Responses 和 Anthropic 的分片、工具调用和结束事件不同。统一 `LLMEvent` 让 AgentLoop 不依赖具体 SDK，便于 Mock、测试和供应商切换。

### Q4：Plan 模式为什么需要模型层和执行器层双重限制？

模型层少暴露写工具可以减少误调用；执行器层是强制边界，防止模型、CLI 或子任务绕过工具列表直接请求写操作。安全检查不能只靠提示词。

### Q5：如何防止文件被别人改过后仍然覆盖？

ReadFile 返回 revision，EditFile/WriteFile 要求 expectedRevision，准备和实际写入前再次核对；不一致就返回冲突。它降低单文件误覆盖，不等价于多文件事务。

### Q6：上下文压缩会不会丢信息？

会省略细节。当前是本地结构化摘录，不是模型摘要；保留系统提示、目标和最近完整调用组，归档历史保存指纹，长结果可以溢写。需要原文时从检查点或溢写存储读取。

### Q7：为什么恢复不能保证 exactly-once？

本地 JSONL 记录和外部 Shell/MCP 副作用不是同一个事务。进程可能在外部成功后、日志落盘前崩溃。因此系统能阻止已确认动作重复，但对不确定的外部动作只能先核验再决定。

### Q8：Hook 修改工具参数后会不会绕过授权？

不会。 `updatedInput` 会替换完整输入，随后重新做 Schema、路径、目标预览和权限检查；原授权只绑定旧的精确参数。

### Q9：Worktree 是不是沙箱？

不是。它隔离 Git 工作文件和 cwd，便于并行修改与审阅 diff，但对象和 refs 共享，批准的 Shell 仍能访问主机。它是协作隔离，不是 OS 安全边界。

### Q10：多 Agent 越多越快吗？

不一定。只有任务独立且足够大时并发才可能降低墙钟时间，同时会增加调用和汇总成本。项目用 FIFO、并发、深度、时间和共享 token 预算控制成本。

### Q11：如何测试真实模型之外的工程行为？

使用脚本化 provider 复现确定的工具调用序列，同时让工具操作真实临时文件、Node 进程、MCP 服务和 Git worktree。这样能验证协议、权限、退出码、恢复和清理；不能替代真实模型能力评估。

### Q12：项目最大的技术风险是什么？

第一是真实模型对不同端点的工具调用和 usage 支持并不一致；第二是 Shell/MCP 不是 OS 沙箱；第三是长任务压缩会丢细节，恢复不能保证外部动作 exactly-once。因此演示和验收必须展示证据和限制。

## 16. 学习路线和代码阅读顺序

### 第一阶段：跑起来

1. 安装 Node.js 24 和依赖。
2. 运行 `npm run demo -- "你好"`。
3. 运行 `npm run chat -- --provider mock --model mock-v1`。
4. 阅读 `src/cli/program.ts`，找出命令如何创建配置、Provider 和 UI。

### 第二阶段：理解 Agent Loop

阅读顺序：

1. `src/providers/types.ts`
2. `src/providers/mock.ts`
3. `src/providers/tool-calls.ts`
4. `src/core/agent-loop.ts`
5. `src/tools/registry.ts`
6. `src/tools/executor.ts`
7. `tests/integration/agent-loop.test.ts`

目标是能回答：模型事件如何结束、工具参数在哪里组装、工具结果如何回填、什么情况下会停止。

### 第三阶段：理解安全边界

阅读 `src/security/paths.ts`、`policy.ts`、`rules.ts`、`audit.ts` 和 `tests/unit/permissions.test.ts`。重点追踪一次 `ask` 工具从请求、准备、审批到执行前复查的完整路径。

### 第四阶段：理解长任务

阅读 `src/core/context.ts`、`session.ts`、`memory.ts` 和对应测试。画出“消息—压缩—溢写—检查点—恢复”的数据流。

### 第五阶段：理解扩展协作

按 `mcp` → `commands`/`skills` → `hooks` → `subagents` → `worktrees` → `teams` 阅读，每个模块先读 `spec.md`，再读实现和 `checklist.md`。

## 17. 项目当前边界和面试表达禁区

可以说：

- 已实现统一 Provider、工具执行、权限、会话、MCP、Skill、Hook 和多任务协作协议。
- 已用 MockProvider 加真实本地资源验证确定性工程行为。
- 已记录跨平台检查、构建和固定离线评估结果。

不要说：

- 真实模型可以稳定修复任意仓库。
- 已测得模型成功率、生产费用节省或并发收益。
- Worktree 提供操作系统级沙箱。
- 上下文压缩语义无损。
- 会话恢复对 Shell/MCP 提供 exactly-once。
- 已完成正式 npm 发布或人工终端体验验收，除非之后确实执行并记录。
